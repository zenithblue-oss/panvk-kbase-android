# 2026-10-21 v7G-E5: vertex_stores, draw_params hang, gs_tess_primitive_id (RC5-dev-v7G-E5)

Input: A06 v7G full run (`device-runs/2026-10-21-a06-v7G-full`, 29/8/1).

## Root causes

1. **vertex_stores iter0..iter5** (`outv[0,16] inconsistent got (1000,1000)`) and
2. **draw_params hang**: both from the jm-v7 046 VS guard (`panvk_v7_lower_vs_ref_guard()`, effective only since it moved after `panvk_lower_nir()` in v7G). For an intrinsic with a result it does `phi = nir_if_phi(&intr->def, undef); nir_def_rewrite_uses_after(&intr->def, phi)`. The intrinsic is in the then block and the phi in the block after the if; `is_instr_between()` returns false for a use in another block, so the phi's own then source is rewritten to the phi too. `phi(phi, undef)` folds to undef: every guarded atomic returns garbage, for every vertex and also for non-indexed draws (the guard is compiled in; `vs_ref_bitmap` 0 only makes `ref` true).
   - vertex_stores: `outv[idx] = atomicAdd(inout[..]) + 1000` is always 1000 (the inout totals are right, only the returned value is lost). In v7G-E the guard ran before `panvk_lower_nir()` and wrapped nothing, so iter passed and indexed_dup failed.
   - draw_params: `idx = atomicAdd(count, 1); rec[idx] = ...` stores at an undefined index, outside the SSBO. It is the only new code path in that test since v7G-E (where it ran and failed 5 cases on a_inst, which 0033 targets); the A06 hung with no result for 10+ min.
   - Fix **0035** (jm-v7 035): after the wrap loop, for each wrapped intrinsic with a result, find the phi in the block after its if whose then-block source is the phi itself and point it back at the intrinsic. The loop lines are unchanged so 0080 (undef -> nir_imm_zero) still applies.
3. **gs_tess_primitive_id**: the 0049 path is gated on `BITSET_TEST(nir->info.system_values_read, SYSTEM_VALUE_PRIMITIVE_ID)`, but the v6/v7 GS compile never gathers info before `panvk_nir_lower_gs()` (comment in `panvk_vX_shader.c`: "nothing gathered info on this NIR yet"). The bit is always clear, so the patch-ID code was never emitted and `load_primitive_id` stayed the triangle ordinal of the TES draw (0..23 for direct, 0..3599 for chunk; matches all `first=` values in the run). Fix **0036** (jm-v7 036): gate on a `load_primitive_id` intrinsic being present (`gs_reads_primitive_id()`). The 0049 math itself matches `poly_tes_patch_id()` (raw id `index_buffer[v0] / POLY_TES_PATCH_ID_STRIDE % patches_per_instance`; the TES draw is one instance, `t->draw[1] = 1`).
