# Patches 130-132: Immortalis-G925 (v13 CSF)

Device: a remote Immortalis-G925 MC12 tablet (gpu_id 0xd8300015, arch v13, kbase CSF uAPI 1.30), reached
through a remote device lab session. The baseline was beta.17 plus 122 (beta.18-dev). All three patches
are in patches/csf-v11/ and committed on main (3dd55ec).

## 130: run v13 vertex stores through gpu_prerast

What: a vertex shader that writes memory (stores or atomics) now gets the gpu_prerast variants on v13+, and
its draws are lowered, the same as on v10-v12. Before this, gpu_prerast skipped side-effect shaders when
PAN_ARCH >= 13, so these draws went through IDVS.

Why: IDVS can run the VS more than once per vertex, so atomic return values were inconsistent.
vertex_stores reported `outv[0,16] inconsistent got (1000,1000)` and draw_params lost vertices
(`first_missing=(100,7,458852,1007)`, 7 cases).

Evidence and results: PanProbe went from 34/36 (beta.17) and 33/36 (beta.18-dev) to 36/36 on the first
run with 130. A second run gave 35/36, and the one failure was the gs_viewport_depth flake that 132 fixes.
v10-v12 do not change, because every condition 130 edits was already true below v13. Draws that
gpu_prerast cannot lower (multi-draw indirect, or a draw larger than the arena) still use IDVS on v13+.

## 131: name Immortalis and small-core GPUs by core count

What: deviceName now comes from the shader core count. One Arm product id covers several product names:
(13,8,0) is G925 Immortalis, G725 or G625; (12,8,0) is G720 or G620; (11,8,2) is G715 or Immortalis-G715.
The split matches panthor. The "Mali-" prefix stays, because apps and PanProbe tests match on "Mali".

Why: pan_model has one row per product id, so the G925 MC12 reported itself as "Mali-G725 MC12".

Evidence and results: the device now reports "Mali-G925-Immortalis MC12". model->name does not change, so
perf counter lookup and logs are not affected. G615 has its own product id and keeps its name.
PanProbe with 130 + 131 gave 35/36, and the one failure was the gs_viewport_depth flake.

## 132: wait for the prerast producer before viewport runs

What: gpu_prerast_draw_generated() now waits on all compute iterator scoreboards before it launches the
viewport run builder (panlib_vp_runs_launch_struct).

Why: when a VS or GS picks the viewport per primitive, a gpu_prerast draw runs three kernels on the
compute queue: the lowered VS, the GS kernel (if there is a GS), and the viewport run builder. The run
builder reads the producer's records and index count, and writes the run list header that the
vertex/tiler queue walks. The producers end with a CSF sync barrier. That barrier only signals the
compute syncobj that the vertex/tiler queue waits on. It does not hold back the next RUN_COMPUTE on the
compute queue, which goes to another iterator scoreboard. So the run builder could start while the GS
kernel was still writing, read a count of zero, and write run_count = 0. The draw then emitted nothing.
The chunk loop and the tessellation path already wait on all iterators before the same launch. Only
the plain path was missing the wait.

Evidence: gs_viewport_depth failed with every pixel left at the clear values in one of its cases
(`FAIL case A_clamp depthL=[1.0..1.0] expL=0.25 badDepth=1024 badColor=1024`), and any of the three cases
could come out empty. Standalone failure counts were 5/10 on beta.17, 4/10 with 130 and 7/8 with 130 + 131.
The test passes on G615 (v11) because that GPU is small enough that the producer finished first. The
genxml for SYNC_ADD64, SYNC_WAIT64 and WAIT is the same on v12 and v13. The viewport depth clamp
emission (VIEWPORT_LOW on v12+) also has no v13-specific branch, so neither one was the cause.

Scope: the race is in shared CSF code, so v10-v12 also get the wait. The cost is one compute-queue wait
per viewport-run draw.

Results on the G925 with 130 + 131 + 132:
- gs_viewport_depth alone: 10/10 PASS.
- PanProbe Run all: 36/36. An earlier Run all gave 35/36 because swapchain_lifecycle failed with no
  surface while the screen was dozing. That test passed twice on its own after waking the screen, and the
  rerun with the screen awake was 36/36.

The run data is in validation/rtl/g925-p132/ and the summary is in validation/rtl/g925-results.txt.
